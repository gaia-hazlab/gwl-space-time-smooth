The Gaia Review Loop

How an issue becomes merged code without a person in the middle of it — and the four places where a person is deliberately put back. Two review loops, one before any code exists and one after, plus the rule that decides which findings are allowed to interrupt someone.

The four dispositions

Every finding this system produces ends in exactly one of four states. Colour carries that state consistently through the whole document — in the stage list, in the diagram, and on the status board.

ProceedNo objection reaches past this issue. Work continues.
DeferredReal, correct, and inside this deliverable. Recorded, published, carried into the implementation prompt — and it does not page anyone.
BlockingA critical concern scoped breaking or wrong-physics. Stops this issue.
Human decidesParked, stalemated, or reserved by policy. Collected and read in one sitting at the end of the run.

One correction to the mental model

The panel reviews the plan, not the fix

The natural way to describe this pipeline is issue → agents fix it → panel reviews the fix → revise. That is not what runs. The science panel reviews a pre-registered plan, before any code exists — this is ground rule 3 (design-review first) made mechanical, on the principle that a flaw caught at the design stage costs one revision rather than a field season.

There is a review-the-code loop, and it is a different instrument: Copilot plus an independent auditor gate, on the PR, after implementation. Both loops exist, both converge on their own terms, and they escalate to a human for different reasons. Keeping them distinct is what lets each one be tuned separately.

The stages

Select and batch

Issues are grouped by milestone, and dependencies that are still open push an issue out of the batch. A batch is a set of siblings, not a chain — which is exactly why one contested plan must not be allowed to discard the others.

gaia_group_issues.pyno model call

Assemble the prior-work brief

Built with no model call from the GitHub graph and our own ledger and corpus: which issues this one references and their state, which PRs already touched it (merged first — those are settled), and what this queue itself already tried, with what outcome. The orchestrator used to be handed three lines and no history, which was both the largest avoidable token cost in the pipeline and a standing risk of redoing settled work.

deterministic

Pre-register the plan

A read-only session states the obstruction, the ordered testable questions, the approach, the artifacts, a declared budget in files / lines / runtime, the stopping conditions, what would count as a reproducible negative result, and what is out of scope. It is schema-validated and fails closed — an unparseable plan is not a plan. A plan declaring more than 40 files or 4000 lines is rejected outright: an agent may not pre-authorise a sprawling diff by predicting one.

gaia-study-designerfails closed

Panel, round 1 — before any code exists

Personas are routed from the issue's own labels and milestone, capped at three, with the auditor on every panel (ground rule 1: the maker is never the sole judge). Every persona is read-only by tool grant, so this stage physically cannot touch the tree. Every concern must name a decisive test — a concern with no test that would settle it is an opinion, and opinions do not block work.

read-only by tool grantdecisive test required

Revise, then adjudicate — the same items, not a fresh review

Only the blocking concerns are fed back to the planner; handing it all forty-one is not a redirection, it is scope creep with a review as its excuse. Round 2 then hands each persona its own previous verdict — not the panel's — plus the diff of what changed, and it must rule resolved / unresolved / withdrawn on each before raising anything new.

blocking concerns onlystalemate → human

Implement

The gaia agents do the work, and every deferred concern is carried into the implementation prompt as a must-address item, with the instruction to file a follow-up issue for anything that would widen the plan.

work proceedsdeferred concerns carried in

Gate integrity, then the mechanical gates

An agent told to make the tests pass has two routes: fix the code, or soften the gate. The second is invisible in a green CI run, and lethal in a numerics repository. The staged diff is checked for added skip/xfail, raised tolerances, raised assertion bounds, and altered gate definitions. Then pixi run test, the DOI check, and the quarto render.

gaia_gate_integrity.pywarning, not block, on net test loss

Open the PR — one per batch

Closes #N lines are rebuilt from the issues that actually committed, on every landing, and any closing keyword written for a parked issue is stripped from the PR body before merge. An issue we cannot prove was resolved stays open.

closure follows what landed

The Copilot loop — convergence by fingerprint

Copilot never submits APPROVED, only COMMENTED, so waiting for approval would hang forever. Convergence is defined by content: a sha256 of the inline comments plus review body. When the fingerprint stops changing, the loop stops — capped at three rounds. A failed API fetch is not allowed to look like "no comments"; it goes to a human.

max 3 roundsfetch failure → human

The auditor gate — and only then, merge

An unchanged fingerprint reads identically whether the revision pass addressed the feedback or ignored it. That ambiguity is exactly why an independent auditor sits downstream: a merge needs both signals — Copilot quiet and an independent auditor satisfied and CI green. An unparseable auditor verdict blocks.

fails closedmerge

End of run — one sitting

Parked issues and the standing-concern digest print once, together, at the end, and explicitly separate from each other. One review sitting instead of one interruption per contested plan.

parked liststanding digest

How the panel is grounded in physics

A review panel is only worth its cost if its members can be wrong about something specific. Four mechanisms put actual physics behind the verdicts, rather than plausible-sounding review prose.

1 · The reviewers were derived from this repository's own review record

The domain personas are specific to this twin (.claude/agents/twin-*.md), not the general gaia family, because a generic reviewer does not know this project's history. Each was built from the record — docs/reviews/peer_review.md, the sensor-uncertainty and covariance review, the 2026-08 hydrologic-state and prior audit — and carries that record's ranked concerns as priors to verify. A generic "theoretician" does not know that an 18.5 m baseline RMSE cannot serve a sub-metre liquefaction requirement, or that ΔD = −Δh_wt makes two prior entries an error. These do.

2 · The invariants are written down, so a violation is checkable

The physics is not left implicit in a reviewer's judgment. It is in the repository as contracts a concern can point at: ΔD = −Δh_wt in src/models/hydro_state.py; the CRS, unit and CF-attribute rules in docs/gaia-conventions.md; the RANGE_CONVENTION and the categorical-layer rule that class codes are never interpolated. A finding that says "this violates the project's own invariant, at this line" is a different object from one that says "this seems wrong".

3 · Every concern must name the experiment that settles it

This is a hard requirement of the panel contract, and it is what turns a review into physics rather than opinion. The #186 panel did not report "the normal-score transform looks wrong". It reported: fit QuantileTransformer on n ∈ {30,100,500,800} iid N(0,1) draws and print z.var(); then simulate a GRF with known sill and range at those n locations, fit the variogram on both z_nst and van-der-Waerden scores, and compare recovered parameters to truth. That is a falsification procedure with a stated threshold. Anyone can run it, and it ends the argument in one direction or the other.

4 · The reviewer's identity is verified, not assumed

"Use the gaia-auditor agent" is prose. Whether the session actually delegated — and therefore whether that persona's system prompt, tool grant and model tier were ever loaded — is a fact recorded in the transcript as a Task dispatch carrying a subagent_type. A verdict from a session that never dispatched is the base model in costume: the persona's name, none of its charter. Every panel call is checked for the expected dispatch, and a missing one fails closed to a block. Preflight refuses to start if a persona file is missing, because a silently degraded judge that still returns confident verdicts is worse than a batch that refuses to begin.

Who sits on the panel — and who is left off

Adding a reviewer without standing on the question is not a free extra opinion. It costs a full model call, and it dilutes the signal: a persona with no expertise in the matter will still produce fluent, plausible concerns, which then compete for attention with the ones that came from actual domain knowledge. So the panel is routed, and capped at three.

The routing rule

gaia-auditor is on every panel — always, ground rule 1. Then the issue's milestone is matched first, because milestones are curated epics and carry more signal than any single label; then its labels. At most two routed personas join the auditor. An issue whose plan text claims novelty or impact (novel, first, outperform, breakthrough…) additionally faces the prior-art and impact readers whatever its labels say — an unchallenged novelty claim is the classic way overreach ships. An unlabelled issue still gets a second pair of eyes, and it is a project persona rather than a generic one, because an unlabelled issue in this repo is still about this twin.

A panel is not a quorum. It is the set of people who could be specifically wrong about this question.

The human: two channels, and they are not the same channel

This is the distinction that most often collapses in an autonomous pipeline, and keeping it open is most of what makes the system usable. Being called and being able to see are different needs, with different latencies and different failure modes.

The second column is why the plan is posted before the code exists. Scientific reasoning that only appears in a merged diff has to be reconstructed backwards from what shipped. Posted at plan time, it is a record of what the group intended and what its reviewers objected to, at the one moment the objection could still have changed the answer.

Why deferred findings must never page

Twelve critical concerns on one issue's plan is not a reason to call twelve times. It is a reason to ask which of them reach past this issue. Severity is a property of the finding; scope is a property of the consequence; only consequence justifies an interruption. Deferred is not discarded — it is posted, recorded, and handed to the implementer — and the panel prompt says so explicitly, because a reviewer who believes a finding will be dropped learns to inflate its scope until it is heard.

The chair: particular panel, holistic reader

The panel is deliberately narrow: three reviewers, routed to this one issue, each ruling only on concerns that are its own. That narrowness is what makes the verdicts sharp. It is also what makes them unreadable in aggregate — three reviewers filing forty-one separately-scoped concerns is a database, and the questions a scientist actually arrives with (do they agree? where do they conflict? what happens next?) are answerable only by reading all of it and holding it in your head.

So the panel summarises, and the split of labour inside that summary is the integrity property:

  • Mechanical, and impossible to fabricate. Which reviewers converged on the same referent — file, symbol, named method — rarity-weighted so that sharing interpolate_residuals.py when six concerns mention it does not count as agreement. Plus the critical-issue list, taken verbatim from the aggregate the gate itself acted on, so the summary cannot describe a decision other than the one made.
  • Judged, by a chair. What the disagreements actually are, and what the panel's own decisive tests imply should happen next. No mechanical rule reads scientific conflict out of prose.

The chair is dispatched as the lab-notebook persona — the documenter — precisely because it has no scientific stake to add. Its instruction is explicit: you report the panel, you do not join it; do not introduce a concern no reviewer raised, do not re-rank the critical issues, do not argue with a verdict; where reviewers conflict, say so plainly and attribute it — do not adjudicate. It runs only after the decision, the blocking concerns and the stalemate flag are already fixed, and it cannot change them. Which is what licenses the one exception to fail-closed:

Fail closed on anything that gates. Fail soft on anything that only describes.

Open gap — the chair is not yet holistic

The chair today is per-issue. It is handed panel.json for this panel and nothing else (gaia_panel.py --brief), so it cannot say "this is the third panel this milestone to raise the out-of-fold coverage cluster" — because it has never been told there were others.

The cross-issue memory does exist: the standing ledger accumulates every deferred concern and groups them by shared referent, turning 31 objections from the #186 panel into seven groups. But the ledger prints at the end of the run, to a human. Nothing connects it to the chair.

The fix is small and safe. convergence() already imports referents() and affinity() from the ledger module, so intersecting this panel's referents against the standing groups is cheap. Passing those matching groups into the chair brief would make the summary say what a returning reader needs: whether this objection is new, or the same standing problem arriving from a fourth direction. It is safe specifically because the chair fails soft and cannot move the gate — the worst case of a wrong match is a misleading sentence in a report, never a wrong decision.

The panel was right and the decision was useless. Everything on the status board above is a consequence of that one run.

The caveat that governs how much this evidence carries

The scope field did not exist when #186 ran. The verdicts on disk carry severity, claim and decisive_test only. Every statement about which of those twelve criticals would have blocked under the current rule is a reading of the concerns, not a measurement of the field in action. The design claim — that reviewers declare scope reliably — is at this writing untested on a live run.

Next, in order

  1. Run round 2 for real. Everything about convergence — the moved count, the stalemate rule, whether withdrawn is used honestly — is pinned by tests and has never met a live panel.
  2. Give the chair the standing ledger. The intersection is cheap, the call site is one function, and it fails soft. This is the gap between "a panel for this issue" and "a reader who holds the project."
  3. Measure scope declaration. Log the observed breaking / wrong-physics / in-milestone split per panel and watch whether it drifts upward as personas learn what stops work.
  4. Detect a hollow withdrawn. One trivial withdrawal manufactures moved > 0 and buys another round. Nothing currently notices.
  5. Bound staleness of parked work. A parked issue whose siblings keep landing gets harder to resume, and nothing measures that.
