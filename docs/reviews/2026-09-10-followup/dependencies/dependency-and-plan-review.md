**Review date:** 2026-09-10. **Scope:** local Fable response, current `BLOCKED_BY`, the probabilistic roadmap, the original 160-issue audit inventory, full archived issue bodies and 74 comments retained in `/tmp/soil-twin-audit`. This is a proposal for review. No issue, label, milestone, GitHub setting or implementation file was changed. GitHub issue state was not refreshed live in this sub-review.

Fable is right to let supervised science work proceed while the runner contract is redesigned. The revised plan needs a scoped dependency model before its stage numbering can govern execution. A scientific prototype, a schema contract, a measured-data acceptance result and an operational release are different deliverables even when they share one issue number.

## Changes to the revised plan

1. **Make the foundation lanes concurrent with runner engineering.** Fable says science should precede the runner redesign, but its “Stages 3 onward” literally places data fixtures, storage/timestep work and schema/UQ foundations after every Stage 2 runner repair. Those are prerequisites for the scientific evidence, and some are already needed by Stage 1's tests. State explicitly that Stage 2 gates unattended execution only. The four foundation lanes in the original roadmap review can run under supervised PR review concurrently: #153/#155/#156 fixtures, #52/#187 schema, #186 estimator/uncertainty, and #89/#172/#137 coordinated storage physics.
2. **Use #25 for bibliography verification.** Stage 1.6 says “none yet, open one,” but existing open [#25](https://github.com/gaia-hazlab/gwl-space-time-smooth/issues/25) is already the standing entry-by-entry bibliography-integrity task. Reconcile or extend it. Closed #158 is the narrower DOI-resolution CI implementation; it does not supersede metadata/content verification.
3. **Preserve what #163 already delivered.** Its [August status comment](https://github.com/gaia-hazlab/gwl-space-time-smooth/issues/163#issuecomment-5357194639) explicitly says scalability moved to #154 and landed via #216. Three of four revised criteria were met; barrier approximation metadata remained open, with domain labels and soft connectivity longer-term. The older probabilistic roadmap's “remaining scalable part of #163” is stale. Do not order a new SPDE scalability project just because #163 remains open. Full-domain workload evidence is a separate requirement from reimplementing the accepted backend.
4. **Treat #163's invalid verdict as a retryable infrastructure failure, without erasing scientific scope.** A valid verdict from every seat is necessary, but “valid” includes revise or block. Stage 0.4 needs accepted scope, preserved substantive concerns, an approved panel outcome, and a documented human release of the existing hold. A parser repair does not by itself release the issue or close the remaining barrier criterion.
5. **Keep the user's Vs30 pause operative.** [ROADMAP.md, v0.3](https://github.com/gaia-hazlab/gwl-space-time-smooth/blob/docs/soil-twin-audit-and-plan-revision-2026-09-10/ROADMAP.md) records that #81–#86 are paused until water-budget work lands. Ordering #81 before #83–#86 is insufficient if the queue can run the whole milestone while it is still paused. #81's own body gates every other issue in that milestone, including #82. Preserve that existing scope; a later human-approved split could allow an independent data-fetch or mathematical prototype, but it cannot infer approval to resume from issue order alone.
6. **Stage 1.1 is a bounded repair within #172, not completion of #172.** Its issue body requires an explicit unsaturated/transit store as well as conserved coupling. Even a perfect capillary transfer debit would leave that scope open. The root review's additional signed-recession reproduction also shows why the acceptance test must account for every boundary flux and storage convention, not merely reproduce one capillary-on/off pair.

## Make the acceptance criteria decisive

- **Stage 0.2:** written policy should name the actual invocation/settings used for supervised draft-only operation. Show that a dry-run with fake `gh` cannot merge or mark ready. A documentation sentence does not change the current runner's merge behavior.
- **Stage 0.4:** require no missing/invalid seat, all mandatory criteria resolved, a valid converged approval tied to the plan revision, and explicit hold release. “Every seat returned a valid verdict” can still mean unanimous rejection.
- **Stage 1.1:** predeclare storage units and control volume; test signed external boundary fluxes and nonnegative inventory, wet/dry and limiting states, capillary-off controls, and timestep refinement. Label a capillary-debit PR as a subtask of #172 until its vadose-store requirement is accepted or formally rescoped.
- **Stage 1.4:** “No 1 km, monthly or LightGBM instruction remains” is too broad. Historical comparisons and native monthly inputs can be correct. Require that active agent instructions and product claims describe the current pipeline and explicitly label historical or optional configurations.
- **Stage 1.5:** reconcile the 23 tracker conflicts individually, recording implemented/partial/superseded/deferred outcomes and acceptance evidence. Matching checkboxes to GitHub state alone may simply preserve an incorrect closure.
- **Stage 1.6:** “Zero mismatches” should distinguish resolved matches, mismatched DOI metadata, incomplete metadata and unresolvable records. A check that cannot retrieve a record must report unknown, not pass it. Use existing #25.
- **Stage 2.5:** an “unseated” log line is not sufficient for a mandatory reviewer. An unseated mandatory role must block approval; optional extra perspectives may be visible without blocking.
- **Stage 2.7:** test scope-aware eligibility, a hold surviving explicit issue selection, missing dependency IDs/types, epic rejection, cycles, already-landed artifacts, stale issue closure, conditional diagnostic activation, and refresh after each accepted or parked issue. The two named topological examples alone do not establish a usable registry.
